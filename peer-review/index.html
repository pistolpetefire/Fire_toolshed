A review record, not an automatic approval

  1. Case Setup: identify the submittal phase, reviewer, scope and governing editions. Select disciplines and generate starter records. Add project-specific requirements.
  2. Documents: register what you expect and what you received. Record revisions. Explain not-applicable and deferred items.
  3. Review Coverage: record applicability, result, evidence and reviewer notes. Unknown is different from not applicable. A documented disposition counts toward coverage; it does not mean acceptable.
  4. Findings: create an internal candidate. Validate only with a source, technical reference and required action. Alternatively create an outstanding need, defer with a milestone, record a limitation, or retain it as not a finding.
  5. Outstanding Needs: identify what is missing, why, who provides it, and when. Received is not resolved. Open items needed before final review block a final conclusion. A stated limitation needs an explicit reviewer explanation.
  6. Report: preview four ordered sections, add your firm name and conclusion, then print to PDF or download a Word-compatible HTML report. Unvalidated candidates are excluded from findings; the report notes that internal review items remain.

EOR / designer QC: Issue draft comments using Review decision. Enter the reviewer name directly in that dialog. In Work Queue, designers record corrections, disagreements, questions or progress. Only the EOR review action closes or withdraws a comment. Corrected responses require a drawing reference; closure requires verification evidence. Roles guide local work and are not authenticated permissions.

Response handoff: Export the full case JSON from this version before sending it to the designer; that assigns a stable case identity. The designer imports that case and exports designer responses from Work Queue. The EOR previews and imports only non-conflicting responses. Changed comments, changed EOR decisions, conflicting response histories and other cases are rejected or skipped. Duplicate responses are ignored. Older case JSON files remain importable. Keep dated full-case backups; avoid editing different copies at the same time.

Portable files: Export after each review session. JSON includes stable IDs, evidence references and activity history. Import also accepts technical-review module JSON: review the target project and record counts before confirming. Changed module snapshots supersede earlier checklist/document coverage; older findings and outstanding needs remain for explicit disposition. Import replaces the active local case after confirmation. Actual source documents are not embedded. Storage is per browser and device, not shared or backed up automatically.

Technical evidence: open an existing calculator, save its output, then record its name, version, run date, result and file reference here. No calculation data is transferred automatically.

Readiness: final issuance requires completed scoped coverage, no undispositioned candidates, required setup information and no open final-review needs. Open validated findings may remain in a final report. Phase percentages describe the submission, not compliance.

Typed names and timestamps provide a local history, not authenticated signatures or tamper-proof issued records.
